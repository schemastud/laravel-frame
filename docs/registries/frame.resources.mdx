# Frame resources

Frame draws list, form and detail screens from a **resource definition**: a key such as `plans`,
the Data class its rows are shaped by, its form and layout, its navigation label, and what a user
may do with it. `frame.resources` is where Frame finds those definitions. Its entries are not the
definitions themselves, though. Each entry is a **producer**: a whole registry of definitions,
attached under a short name. Frame asks its producers, and the producers answer.

Frame owns the port and stays independent of the declaration mechanism. Beam is its producer:
`#[ParticleResource]` supplies the declaration that serves both Beam's REST API and Frame's screens.

## What ships

Frame's service provider binds the `ResourceRegistry` port to the composite registry and attaches
its in-memory `frame` store. Beam fills the registry through its `beam` adapter, projecting resources
from `#[ParticleResource]` declarations rather than requiring hand-built definitions in a host.
See [`beam.particle.resources`](https://github.com/splicewire/laravel-beam/blob/main/docs/registries/beam.particle.resources.mdx).

`form` defaults to `enriched`, which draws each declared widget; `bare` is the plain-data mode. Any
other value is refused when the definition is built (`Schemastud\Frame\Registry\FormMode`).
The [attribute reference](../attributes.md) covers declarations and their doctor checks.

## Attaching a producer

The index can hold more than one producer.
Attaching another producer is not a supported extension point today; Beam is the one producer.

## Two questions, two halves

This registry answers two different questions, and it keeps them apart:

- **About producers** — `keys()`, `resolve()` and `tryResolve()` work over members.
  `keys()` returns `frame.resources.frame`, `frame.resources.beam` and so on.
- **About resources** — `has()`, `get()`, `find()` and `all()` work over the definitions the
  members produce. These are what Frame's controllers call with a resource key from the URL.

So `has('plans')` asks whether any producer has a framed resource called `plans`, never whether a
member exists. Each producer keeps its own rules about what it exposes, and the composite delegates
to them rather than flattening them.

## When two producers have the same resource

That is allowed, and the **last attached member wins**: a keyed read asks the members in reverse
attachment order and returns the first answer. The displaced definition is still readable through
its own member. `all()` asks every member. Attaching a second member under a name already taken
replaces that member, which is the
[**duplicate-key policy**](/beam/docs/foundations/registries#key-policies), **supersede**, at
work.

## Who reads it

Frame's routes read it on every request: `GET /frame/manifest` lists the resources the current user
may reach, and `/frame/resources/{resource}` with its `schema`, `records` and action routes resolve
one definition by key. An application that attaches no producer at all is legal; its manifest
serves an empty resource list.
